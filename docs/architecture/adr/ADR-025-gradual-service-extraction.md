# ADR-025 — Постепенное выделение сервисов из модульного монолита

- Status: **Proposed** (2026-11-24). Решение владельца требуется до первого выделения; до тех пор действует единый deployable ([ADR-001](ADR-001-backend-architecture-style.md), Конституция §3.2).
- Scope: условия, порядок и техника выделения доменов; что допустимо делать уже сейчас
- Builds on: [ADR-021](ADR-021-partner-directory-contract.md), [ADR-022](ADR-022-transactional-outbox.md), [ADR-023](ADR-023-build-system-and-module-structure.md), [microservice-readiness](../microservice-readiness.md)

## Context
Аудит 2026-11-24 показал: границы Gradle-модулей честные (нет циклов, `platform` чист), но **данные и поведение связаны**: 144 связи в baseline (42 импорта, 102 SQL), один узел циклов из 10 пакетов, 123 внешних ключа между владельцами, Admin читает таблицы 8 доменов, события не публикует никто. Выделение сегодня означало бы переписывание, а не перенос. При этом разделять систему «по моде» нельзя: каждый сервис — отдельный деплой, мониторинг, дежурство, распределённые транзакции и расходы.

## Alternatives
1. **Разделить сейчас по Gradle-модулям.** Отвергнуто: связи через SQL/FK, узел циклов; потребовало бы распределённых транзакций в каждом сквозном потоке.
2. **Остаться монолитом навсегда и не готовиться.** Отвергнуто: стоимость выделения растёт с каждой новой чужой SQL-связью; ратчеты бесплатны.
3. **Готовить границы внутри монолита и выделять по измеримому триггеру (выбрано).**

## Decision
1. **Сейчас — только подготовка внутри монолита**: ратчеты ([fitness-functions](../fitness-functions.md)), контракты вместо SQL (`PartnerDirectory`, `<Domain>AdminApi`), события через outbox (нефинансовые первыми), контрактные тесты. Физическое разделение, отдельные БД, Kafka, Kubernetes, Redis, Service Mesh — **запрещены** без отдельного решения и доказанной необходимости.
2. **Триггер выделения** (нужен хотя бы один, измеренный): независимое масштабирование/ресурсы (например, GPS-поток вытесняет API на одной JVM/БД, p95 > SLO), регуляторная или security-граница, отдельная команда и цикл релизов, изоляция отказов. «Чище архитектура» — не триггер.
3. **Ворота кандидата** (все обязательны, проверяются автоматически там, где можно):
   - домен вне узла циклов (`known-coupling-cycles.txt` не содержит его рёбер);
   - нет входящих чужих SQL в его таблицы и нет FK из чужих таблиц на его таблицы (кроме ссылок на ядро);
   - все исходящие зависимости — через контракт ядра или события;
   - Admin работает с доменом через `<Domain>AdminApi`;
   - есть версионируемые события, идемпотентные потребители, DLQ с инструментом разбора, retention outbox;
   - контрактные тесты портов и снимок OpenAPI зелёные; `correlation_id` проходит через события и HTTP, включены трассировка и метрики;
   - есть план отката (флаг домена возвращает трафик в монолит) и репетиция восстановления.
4. **Техника (strangler, обратимая):** (а) второй экземпляр **того же артефакта** с включённым одним доменом и маршрутизацией по пути — без изменения кода; (б) один писатель (переключение записи по флагу домена); (в) отдельный артефакт и приложение; (г) **отдельная БД — последним**, через логическую репликацию таблиц домена и окно отката; FK на ядро заменяются идентификатором без ограничения плюс проверка по контракту.
5. **Порядок кандидатов (по данным аудита, не обязательство):** `education` (нет входящих чужих SQL) → `leisure + events` (после переноса админ-SQL) → `food + groceries` (как семья) → `mobility` (`rides + delivery`, после устранения SQL-цикла) → `booking family` (последняя из-за 30 входящих SQL и 19 FK). Ядро (`identity`, `partners`, `admin`, `platform`, `support`) остаётся в монолите. `maps` уже отдельный.
6. **События и согласованность.** Между сервисами — только события (at-least-once, порядок по агрегату, идемпотентный потребитель) и запросы по контракту; сквозные операции с деньгами — сага/компенсации, оформляются отдельным ADR (платежей в коде пока нет). Управляемая eventual consistency: каждое событие имеет владельца, версию и SLO задержки.
7. **Admin** не получает прямого доступа к таблицам выделенного домена: `<Domain>AdminApi` подменяется удалённым адаптером; сквозные дашборды — проекции из событий только при измеренной проблеме.

## Consequences
- Первые PR после принятия — перенос демо-сидов в `app`, `<Domain>AdminApi` для `leisure`/`food`, продюсеры `partner.*`/`offering.*`; каждый уменьшает числа в ратчетах.
- Ворота п.3 частично автоматические (ратчеты), частично — чек-лист PR выделения.
- Стоимость: контракты и события — дополнительный код и тесты; оправдана тем, что делает выделение переносом, а не переписыванием.

## Not decided
Брокер ([ADR-006](ADR-006-messaging-platform.md)), протокол межсервисных вызовов (HTTP/gRPC), платёжный домен и сага, трассировка (OpenTelemetry — по умолчанию), политика версий OpenAPI для внутренних контрактов, момент появления отдельных БД.
