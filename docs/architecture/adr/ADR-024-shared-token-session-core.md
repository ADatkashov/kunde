# ADR-024 — Общее ядро токен-сессии и отдельные адаптеры авторизации

- Status: **Accepted** — владелец утвердил общее ядро токен-сессии с отдельными адаптерами по ролям (2026-11-24, чат).
- Date: 2026-11-24
- Scope: Flutter-приложения Consumer, Partner, Executor, Admin; backend Identity не меняется
- Builds on: ADR-018 (роли Partner/Admin), ADR-023 (раскладка `apps/` и `packages/`), Конституция §9, §11

## Context
До решения было две несвязанные реализации одной и той же задачи: `AuthRepository` (Consumer, Executor, Admin; последовательная очередь операций, формат `issuerVersion/context/refresh/id`) и `PartnerSession` (Partner; single-flight refresh, формат `base/refresh/partnerId`, свои типы ошибок, локальная DEV-фикстура). Обе хранят refresh-токен в защищённом хранилище, держат access-токен в памяти, обновляют его заранее, чистят сессию при отказе сервера и переживают сетевые сбои — то есть повторяли инфраструктурную логику, где ошибка = дыра в безопасности.

## Alternatives
1. **Один универсальный `AuthRepository` для всех ролей** с флагами и ветвлением. Отклонено: смешивает роли, растёт условной логикой, ломает отдельные форматы хранения и ошибки Partner.
2. **Оставить две реализации.** Отклонено: дублирование критичного кода, разные гарантии конкурентности.
3. **Общее ядро жизненного цикла + отдельные адаптеры (выбрано).**

## Decision
Пакет `packages/kunde_session`:
- `TokenSession` — жизненный цикл: `restore`, `signIn`, `accessToken` (автообновление за 30 с до истечения, принудительное обновление), единая очередь операций (при истёкшем токене параллельные вызовы делают **один** refresh; ротируемый refresh-токен тратится один раз; при простое и свежем токене — быстрый путь без очереди), `rejectIfCurrent` (401), `signOut` (локальная очистка сразу, затем отзыв на сервере; результат сервера возвращается), `updateExtras`, `peek`, `discard`; флаги `authenticated`/`expired`, `onExpired`.
- Порты: `SessionPersistence` (хранилище и формат — у адаптера), `TokenRefresher` (сетевой вызов — у адаптера); `SecureKeyValue`/`FlutterSecureKeyValue`/`MemorySecureKeyValue`.
- Типизированные сбои ядра: `SessionMissing`, `SessionRejected` (сессия очищена), `SessionUnavailable` (сессия сохранена). Адаптеры сами переводят их в свои типы.
- Токены — секреты: `IssuedTokens`/`StoredSession` не печатают значения в `toString`, ошибки ядра не несут токенов; в хранилище попадает только refresh и extras, access живёт в памяти.

Адаптеры (авторизация и роль остаются у приложения):
- **Consumer/Operator** — `kunde_auth.AuthRepository` (OIDC или phone OTP; формат хранения и ключ `kunde.consumer.session.v1` сохранены, чтобы установленные приложения не потеряли вход). Executor и Admin используют этот адаптер со своей конфигурацией; их сессии изолированы песочницей ОС (разные applicationId) и контекстом (`apiBase`), ключ хранилища задаётся параметром `SecureTokenVault(key:)`. Токен отправляется только на свой API: другой origin и путь вне API отклоняются до отправки.
- **Partner** — `PartnerSession` (ключ `kunde.partner.session.v1`, формат `base/refresh/partnerId`, свой OTP, `PartnerAuthException`/`SessionExpiredException`, локальная DEV-фикстура, `partnerId` переживает ротацию токенов и повторный вход).

Backend не менялся: те же `auth/otp/request`, `auth/otp/verify`, `auth/token/refresh` (ротация refresh-токена), `auth/logout`.

## Consequences
- Одна проверенная реализация конкурентности, истечения и очистки сессии; новая роль добавляется адаптером, а не копией.
- Тесты: ядро (21 кейс), адаптер Consumer (9), адаптер Partner (9 новых) + прежние тесты обоих; проверяются OTP, восстановление, истечение, ротация, одновременные запросы, logout, сетевые ошибки, недействительный refresh, `partnerId`, изоляция хранилищ и ролей, отсутствие токенов в тексте ошибок, запрет отправки токена на чужой origin.
- Ограничение: Executor и Admin пока используют общий дефолтный ключ хранилища (изоляция — на уровне ОС и контекста API); отдельные ключи по ролям потребуют разового повторного входа, поэтому вводятся только при следующем осознанном изменении формата.
- Не включает: серверную авторизацию (RBAC остаётся на backend; отдельное приложение не граница безопасности).
