# KUNDE Architecture Constitution

Статус: **действует с 2026-11-24** (утверждена владельцем вместе с [ADR-023](adr/ADR-023-build-system-and-module-structure.md)). Изменение Конституции требует отдельного согласования с владельцем; PR, меняющий этот файл, не смешивается с другими изменениями.

Её читают **до любых правок кода** разработчики, Claude Code, Codex и другие AI-агенты. Правила не дублируются в других файлах — на неё ссылаются ([AGENTS.md](../../AGENTS.md), [CLAUDE.md](../../CLAUDE.md), [DEVELOPER_GUIDE.md](DEVELOPER_GUIDE.md), PR-шаблон).

## Как читать статусы

- **MUST (действует)** — правило соблюдается уже сейчас и проверяется.
- **TARGET (утверждено, реализуется)** — цель утверждена, реализация идёт по плану ADR-023; до завершения допускаются документированные исключения (baseline).
Статус каждого пункта и текущее состояние — в таблице «Состояние реализации» в конце.

## 1. Domain-first
**One Domain — One Canonical Name — One Obvious Location — One Defined Owner.**
1. MUST: у каждого бизнес-домена одно каноническое имя, перечисленное в [Domain Registry](domain-registry.md). Новый домен добавляется в реестр в том же PR.
2. TARGET: расположение домена предсказуемо: `backend/services/<domain>`, `apps/<app>/lib/features/<domain>/`, тесты рядом, префикс таблиц `<domain>_`.
3. MUST: код продукта не лежит в чужих пакетах (Delivery не ищем в Food, Platform или Admin).
4. Бизнес-имя и техническое имя могут различаться (`rides` ↔ «Taxi»), но связь записана в реестре.

## 2. Единые имена
Короткие, без сокращений, без синонимов, одно слово в нижнем регистре (`homeservices`). Запрещены `common`, `utils`, `manager`, `helper` для несвязанной бизнес-логики. Одно понятие — одно имя во всех приложениях и слоях. HTTP-маршруты — публичный контракт: не переименовываются ради косметики.

## 3. Multi-module backend
1. TARGET: Gradle Kotlin DSL; `backend/app` (единственный Spring Boot jar), `backend/platform`, `backend/services/<domain>` (библиотеки, у каждого `build.gradle.kts`), `backend/testing` при необходимости.
2. MUST: один исполняемый Modular Monolith; отдельный runtime на домен не создаётся без отдельного решения.
3. MUST: модули не пустые; модуль на класс не делается; тесно связанный агрегат не режется.
4. Правило зависимостей: `app → всё`; `services/* → platform`; домен → домен только по записанным однонаправленным рёбрам (реестр) через публичный контракт; циклы и обратные рёбра запрещены; `platform` не зависит от `services/*`. Зависимости — `implementation`, `api` только когда тип выходит в публичную сигнатуру.
5. MUST: новая междоменная связь (импорт или SQL) не добавляется; `ArchitectureBoundariesTest` — ратчет, baseline может только уменьшаться.
6. Внутри модуля: `api` / `application` / `domain` / `infrastructure` пропорционально размеру (плоский модуль до ~15 файлов); интерфейс на каждый класс не создаётся.

## 4. Ответственность platform
`platform` — только техника: security, конфигурация, observability, технические события (outbox/inbox), geo-примитивы, placement, технические контракты. **Бизнес-понятия (Order, Fulfillment, Payment, доменные правила) в `platform` не живут**, даже если ими пользуются несколько продуктов: критерий — владение ответственностью, а не повторное использование. Контракт, нужный двум доменам, ставится в `platform` только если он технический (например `RoutingProvider`, `PartnerDirectory` как порт); иначе — публичный контракт домена-владельца.

## 5. Владение данными
Каждая таблица имеет владельца ([`table-owners.txt`](../../backend/src/test/resources/architecture/table-owners.txt); тест падает на сироте). Чужие таблицы читаются только через контракт владельца. Применённые миграции Flyway не меняются и не переименовываются; миграции — одно дерево, порядок версий общий. Отдельной БД на модуль нет.

## 6. Готовность к микросервисам
Каждый домен должен выделяться с минимальными изменениями: публичный контракт, явные зависимости, собственные данные и тесты. Выделение сервисов сейчас не выполняется ([microservice-readiness](microservice-readiness.md)).

## 7. Масштабирование БД и многоэкземплярность
Сохраняются City placement registry, `ShardResolver`, `PlacementService`, локаторы агрегатов ([database-sharding-readiness](database-sharding-readiness.md)). Физический sharding — только по отдельному решению. Код не хранит состояние в памяти процесса, которое должно быть общим (idempotency, очереди — в БД/outbox); фоновые задачи безопасны при нескольких экземплярах.

## 8. Совместимость API
Публичные маршруты сохраняются, если изменение не даёт архитектурной пользы. Фундаментально плохой API исправляется с обновлением OpenAPI, DTO, клиентов всех приложений, тестов и с переходным периодом для установленных APK. Новая сборка backend не должна ломать опубликованные клиенты.

## 9. Безопасность
Fail-closed JWT/OIDC, права проверяются на backend (**отдельное приложение не граница безопасности**), security gates и baseline не ослабляются, секреты не коммитятся ([AGENTS.md](../../AGENTS.md)).

## 10. Тестирование
Тесты домена — в модуле домена и повторяют его структуру; архитектурные, ownership, Flyway, API-совместимость и E2E — общие. Тест не удаляется ради зелёной сборки; golden-файлы не обновляются без просмотра; отчёт говорит только о реально запущенном.

## 11. Четыре независимых приложения
TARGET: `apps/{consumer,partner,executor,admin}` — каждое со своим `pubspec.yaml`, entrypoint, конфигурацией, навигацией, features, тестами, сборкой и CI; общий код — только в `packages/*` и только реально общий (`design_system`, `api_client`, `localization`); бизнес-логика приложений в один общий пакет не сливается. Application ID и подпись существующих приложений не меняются. Flutter не дублирует бизнес-правила backend. Features создаются только для реально существующих экранов.

## 12. Future-proof engineering
Фундаментальное решение, которое позже потребует дорогой переработки (Backend, Flutter, API, данные), принимается сейчас; инфраструктура без реальной потребности не внедряется. Правильная структура важнее сохранения неудобной исторической, но работающий функционал сохраняется.
