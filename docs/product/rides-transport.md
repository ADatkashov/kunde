## Backend

Модуль `kz.kunde.rides` содержит правила переходов, расчёт тарифа в KZT и ранжирование по географической близости. Ранжирование исключает устаревшие координаты, неподтверждённых и занятых водителей, неподходящий класс, неодобренное авто и переданные в список исключений идентификаторы. Ранжирование ещё не резервирует водителя и не отправляет оффер. Тариф не получает значения по умолчанию. Проверка предложения при выдаче котировки относится к следующему этапу.

`POST /api/v1/rides/route-preview` принимает координаты начала и конца через существующую consumer policy. При отключении хотя бы одного из двух флагов возвращает `RIDES_UNAVAILABLE`. При отсутствии адаптера возвращает `RIDES_ROUTING_UNAVAILABLE`. Успешный ответ содержит дорожную геометрию, расстояние и длительность от адаптера и возвращается с заголовком `Cache-Control: no-store`. Запрос не сохраняет координаты и не создаёт поездку. `POST /api/v1/rides/address-search` и `POST /api/v1/rides/reverse-geocode` используют тот же адаптер и ограничения доступа, принимают язык RU/KK/EN и возвращают адреса с координатами.

## Хранение и Consumer API

Flyway V22 добавляет `transactions.ride_fare_quotes`, `transactions.rides` и `transactions.ride_events`. Котировка привязана к `identity.users`, содержит версию тарифа и параметры маршрута. База ограничивает одну ожидающую поездку на клиента и одно использование котировки, запрещает изменение котировки и удаление или изменение событий. Координаты котировки не возвращаются из истории. До добавления реальных данных требуется утвердить срок хранения координат.

- `POST /api/v1/rides` создаёт `REQUESTED` из действующей котировки владельца. Повтор с тем же ключом и котировкой возвращает исходную запись.
- `GET /api/v1/rides` и `GET /api/v1/rides/{rideId}` возвращают поездки владельца.
- `POST /api/v1/rides/{rideId}/cancel` идемпотентно отменяет ожидающую поездку. Отключение новых поездок сохраняет доступ к истории, отмене и повтору уже сохранённого ключа.

`POST /api/v1/rides/quotes` рассчитывает цену по параметрам маршрута из адаптера и версии тарифа из конфигурации backend. Для каждого доступного класса задаются `version`, `base-kzt`, `per-kilometer-kzt`, `per-minute-kzt`, `minimum-kzt` и `fixed-fee-kzt` в `app.rides.pricing.tariffs.<class>`. Значений тарифов по умолчанию нет. `app.rides.pricing.quote-lifetime-seconds` задаёт срок действия котировки, по умолчанию 120 секунд. Класс определяется конфигурацией тарифа. Фактическая доступность водителей пока не проверяется при выдаче котировки.

Детерминированный адаптер подключается только через `RIDES_SYNTHETIC_ROUTING_ENABLED=true` в явной среде DEV/TEST с включённым Rides. В обычном режиме без провайдера геокодирование недоступно. Интеграционный тест получает котировку через HTTP, проверяет изоляцию владельца и оформляет заявку из этой котировки. Flyway V23 расширяет V22 состояниями поездки, профилями, автомобилями, офферами и аудитом модерации. Кандидаты отбираются по одобренному профилю и автомобилю, онлайн-режиму, классу и свежему местоположению. Индексы и блокировки разрешают одну активную поездку на водителя и клиента.

- Клиент запускает или повторяет подбор через `POST /api/v1/rides/{rideId}/dispatch`. Пилот использует повторный вызов для выдачи следующего оффера после отказа или таймаута. Длительность оффера 25 секунд. Через 2 минуты поиска следующий вызов завершает подбор при отсутствии действующего оффера.
- `/api/v1/executor/rides` использует каноническую сессию. Поддерживаются регистрация профиля и одного автомобиля, доступность, обновление координат, выдача офферов, ответ, переходы назначенной поездки и история водителя.
- `GET /api/v1/rides/{rideId}/location` возвращает свежую позицию назначенного водителя только владельцу активной поездки. После завершения позиция недоступна. Статус offline и блокировка очищают позицию.
- `/api/v1/admin/rides/drivers` использует действующий административный scope и отдельный grant `RIDE_VERIFICATION`, который выдаётся вне API. Решения по профилю и автомобилю записываются в неизменяемый журнал. Проверка файлов документов, автопарки и жалобы остаются открытыми.

## Feature Flags

Все шесть флагов читаются из конфигурации backend и по умолчанию выключены.

| Свойство | Переменная окружения |
| --- | --- |
| `app.rides.enabled` | `RIDES_ENABLED` |
| `app.rides.consumer-enabled` | `RIDES_CONSUMER_ENABLED` |
| `app.rides.executor-enabled` | `RIDES_EXECUTOR_ENABLED` |
| `app.rides.partner-enabled` | `RIDES_PARTNER_ENABLED` |
| `app.rides.dispatch-enabled` | `RIDES_DISPATCH_ENABLED` |
| `app.rides.payments-enabled` | `RIDES_PAYMENTS_ENABLED` |

Backend принимает включение общего флага только в явном `dev`, `local` или `test` и при включённой канонической identity. Активный профиль `prod` или `production` и попытка включить платежи вызывают отказ при старте. `executor`, `partner` и `dispatch` зарезервированы для соответствующих API. Флаги читаются при старте. Управление из Admin и динамическая конфигурация ещё отсутствуют. При расширении API флаг новых поездок должен блокировать создание и новые офферы отдельно от чтения, помощи, отмены и безопасного завершения активных поездок.

## Оставшиеся этапы

1. Проверка конкурентного принятия на PostgreSQL, управление автомобилями и документами, критерии проверки водителя и автопарка, фоновые таймауты.
2. Consumer, Executor, Partner и Admin, совместная проверка жизненного цикла с синтетическими данными.
3. Подтверждение провайдера карт и методов оплаты, требований к лицензированию перевозок, защите и хранению документов и координат, обработке инцидентов в Казахстане.
4. Тесты на устройствах и подписанные DEV Release APK после реализации клиентских сценариев.

Публичная активация выполняется отдельно по решению владельца после общей интеграционной проверки набора сервисов.

## Executor Flutter

`mobile/lib/executor_main.dart` запускает отдельный интерфейс водителя с существующим телефонным Identity. Android сборка устанавливается как `com.kunde.executor`. Consumer сохраняет свой ID и входной файл.

Executor регистрирует профиль и один автомобиль, показывает проверку, принимает или отклоняет офферы, отправляет действия поездки и читает историю. Перед включением онлайн-режима приложение запрашивает разрешение геопозиции. Позиции отправляются только при явном включении и нахождении приложения на переднем плане. Consumer показывает координаты, когда backend возвращает свежую позицию назначенного водителя. Карта пока не подключена.

В workflow **Android Release APK (DEV)** параметр `executor` выбирает приложение. Workflow использует существующую подпись и проверяет APK, имя пакета, сертификат и SHA-256. До прохождения E2E и сборки ссылки на артефакты отсутствуют.

## Детерминированный маршрут DEV/TEST

Для изолированного экземпляра включить внутренние флаги Consumer, Executor, Dispatch и `RIDES_SYNTHETIC_ROUTING_ENABLED`. Настроить тариф Economy и использовать тестовые аккаунты Identity. Поиск `Synthetic` находит две явно обозначенные точки; поддерживается только маршрут между ними в направлении pickup → destination. Для проверки назначения тестовый водитель должен находиться рядом с точкой подачи. Флаг выключен по умолчанию и несовместим с PROD. V24 сохраняет признак тестового маршрута в котировке, а после выключения тестовой маршрутизации новые заявки из этих котировок отклоняются. Активные тестовые поездки сохраняют маркировку и могут завершаться.

## Автопарк Partner

Флаг `RIDES_PARTNER_ENABLED` открывает вход в «Автопарк» из вкладки «Заведение». Владелец уже одобренной организации подаёт заявку, администратор с `RIDE_VERIFICATION` рассматривает её через API. Доступ сотрудников повторно проверяется backend. Владелец или менеджер одобренного автопарка назначает водителей из активных сотрудников. Смена автопарка во время активной поездки запрещена. V25 фиксирует принадлежность в момент назначения поездки, чтобы история не переходила между организациями. В интерфейсе доступны статус автопарка, состав, автомобили, поездки и агрегированные счётчики. Синтетические поездки маркируются и исключены из счётчиков.

Защищённые API администрирования возвращают неизменяемый аудит решений по водителям, автомобилям и автопаркам. Проверка файлов документов остаётся отдельным этапом.

## Административные операции и жалобы

`mobile/lib/admin_rides_main.dart` использует существующий телефонный Identity. Модерация и блокировки водителей, автомобилей и автопарков требуют `RIDE_VERIFICATION`. Мониторинг поездок и обработка жалоб требуют отдельного `RIDE_OPERATIONS`. Оба разрешения повторно проверяются backend на каждом запросе. Интерфейс отображает журнал модерации и событий жалобы.

Consumer отправляет жалобу через существующий раздел поддержки внутри поездки. V26 разрешает связать обращение только с поездкой владельца. Оператор закрывает обращение идемпотентно. Журнал фиксирует исполнителя и время. Загрузка и хранение файлов документов остаются открытыми.

## Нативный E2E

Workflow **Rides two-app Android E2E** собирает два debug APK под разными application ID, запускает локальный backend с одноразовым ключом, тестовым PostgreSQL и синтетическими номерами, устанавливает оба приложения на эмулятор, проверяет путь поездки и сохраняет результаты по стадиям. Только debug Executor допускает HTTP на `localhost` для `adb reverse`. Подписанная DEV сборка по-прежнему принимает HTTPS.

Результат считается выполненным только когда артефакт `rides-native-e2e` содержит `status=PASSED`. Нативный debug артефакт не является подписанным DEV Release APK.
