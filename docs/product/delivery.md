# KUNDE Delivery 1.0

Отправная точка аудита — `35d0903edd9a70a91f718278e96efca8e2d8ce13`. На этом коммите есть сценарии самовывоза и контракт fulfillment, а также отдельный продукт Rides. Самостоятельного сервиса отправлений нет. Работа относится к [EP-014 / ADA-18](https://linear.app/adatkashov/issue/ADA-18/ep-014-delivery-and-logistics). Решение D-02 из PRD 1.1 регулирует Food Ordering. Подключение Delivery к заказам Food, Grocery и Flowers требует отдельной проверки совместимости.

## API персональных отправлений

- `POST /api/v1/deliveries/quotes` принимает тип, вес в граммах, три размера в сантиметрах и две точки. Максимум для документов — 2 кг, для остальных типов — 30 кг. Среда может задать меньший лимит. Возвращает KZT, версию ставки, расстояние, оценку времени, время создания и срок действия. `syntheticRoute: true` обозначает тестовый маршрут.
- `POST /api/v1/deliveries` принимает котировку, адреса, имя и телефон получателя, описание, примечание курьеру и явное подтверждение допустимости содержимого. Нужен `Idempotency-Key`. Котировка доступна один раз владельцу в пределах срока действия. Совпадающий повтор возвращает существующую запись, конфликтующий даёт 409.
- `GET /api/v1/deliveries` и `GET /api/v1/deliveries/{id}` возвращают историю и детали владельца с версией тарифа, расстоянием и оценкой времени из сохранённой котировки и заголовком `Cache-Control: no-store`.
- `POST /api/v1/deliveries/{id}/cancel` проводит переход из `CREATED` в `CANCELLED_BY_CUSTOMER`. Повтор безопасен. Создание и отмена фиксируются в неизменяемой истории.

## Внутренняя конфигурация

`DELIVERY_ENABLED` и `DELIVERY_CONSUMER_ENABLED` выключены по умолчанию. Для котировок с существующим тестовым маршрутом требуется `DELIVERY_SYNTHETIC_ROUTING_ENABLED=true`. Установите явные тестовые значения `DELIVERY_BASE_KZT`, `DELIVERY_PER_KM_KZT`, `DELIVERY_PER_KG_KZT` и `DELIVERY_MINIMUM_KZT`. Версия тарифа задаётся `DELIVERY_TARIFF_VERSION`. Значение `DELIVERY_PAYMENTS_ENABLED=true` приводит к отказу при запуске. История и отмена доступны владельцу после выключения приёма заказов.

**Functional DEV/TEST Ready** — критерии ещё открыты.
**External Integration Pending** — дорожный провайдер Алматы, платежи, проверка документов и канал доставки кода вручения.
**Production Launch Blocked** — требуется проверка эксплуатации, юридическое согласование запрещённых отправлений и ответственности, а также политика хранения адресов и контактов. Подтверждение допустимости содержимого в API является декларацией отправителя.

## Диспетчеризация и вручение DEV/TEST

Курьер регистрирует профиль через `POST /api/v1/executor/deliveries/profile`. Администратор с `DELIVERY_OPERATIONS` проверяет очередь `GET /api/v1/admin/deliveries/couriers` и принимает решение через `POST /api/v1/admin/deliveries/couriers/{id}/decision`. Решение включает максимальный вес, габарит и причину. Загрузка и проверка документов остаются отдельной задачей.

Курьер включает доступность и передаёт текущую точку через `PUT /api/v1/executor/deliveries/availability` и `PUT /api/v1/executor/deliveries/location`. Сервис хранит только последнюю точку доступного курьера, принимает обновления с интервалом от пяти секунд и исключает точки старше двух минут из подбора. Эта координата служит подбору кандидатов.

Со стороны отправителя `POST /api/v1/deliveries/{id}/dispatch` начинает или повторяет подбор. Выбирается ближайший совместимый курьер на расстоянии до 5 км по прямой. Оффер действует 25 секунд и доступен только своему кандидату. Отказ сразу запускает повторный подбор. При таймауте клиент повторяет вызов dispatch. Окно подбора составляет две минуты. Принятие выполняется транзакционно. Delivery и Rides сериализуют назначение на общей строке canonical identity.

`GET /api/v1/executor/deliveries/offers` и `POST /api/v1/executor/deliveries/offers/{offerId}/response` обслуживают офферы. Курьер получает список назначенных отправлений через `GET /api/v1/executor/deliveries` и отмечает исполнение через `POST /api/v1/executor/deliveries/{id}/progress`. Завершённая история скрывает адреса и примечание.

Отправитель получает тестовый код через `POST /api/v1/deliveries/{id}/handoff-code` и вручную передаёт его синтетическому получателю. Назначенный курьер вводит код через `POST /api/v1/executor/deliveries/{id}/handoff`. Срок кода 15 минут, лимит пять ошибочных попыток. Повтор запроса во время срока действия возвращает тот же код с оставшимся лимитом. После истечения и до вручения можно выпустить новый код. Backend хранит HMAC, блокирует повторное использование и фиксирует успешное вручение в журнале. После подтверждения доступен переход `COMPLETE`. При недоступном получателе оператор может оформить возврат через `POST /api/v1/admin/deliveries/{id}/return`.

Для новых назначений включите `DELIVERY_EXECUTOR_ENABLED` и `DELIVERY_DISPATCH_ENABLED` в тестовой среде. Передайте `DELIVERY_HANDOFF_KEY` через конфигурацию секретов с минимумом 32 байт. Сохраняйте тот же ключ на время активных тестовых вручений. При отключении приёма новых заказов текущие назначения могут продолжить жизненный цикл и подтвердить вручение с тем же ключом.

## Consumer DEV/TEST

Карточка «Доставка» открывается после входа, когда `/api/v1/capabilities` возвращает `deliveryEnabled=true`. Используйте сохранённые адреса профиля. При `deliverySyntheticRouting=true` экран отдельно предлагает фиксированные тестовые точки. Подтверждение использует одну котировку и тот же ключ при повторе сетевого запроса.

После создания экран деталей запускает подбор и обновляет состояние доставки. История доступна с экрана Delivery. В состоянии «В пути» отправитель может получить одноразовый код для ручной передачи в DEV/TEST. Клиент отображает стоимость из backend, статус, курьера и признак тестового маршрута. Повтор формирует новый черновик и требует новой котировки и подтверждения. После завершения владелец может отправить оценку назначенного курьера через `POST /api/v1/deliveries/{id}/rating`.

## Executor DEV/TEST

В KUNDE Executor режим «Доставка» открывается при `deliveryExecutorEnabled=true`. Он использует текущую сессию и отдельный допуск курьера. После подтверждения профиля оператором курьер включает доступность и передаёт текущую точку по явному действию. Для синтетического режима доступна отдельно маркированная тестовая точка. Экран показывает офферы и назначенные отправления, проверяет одноразовый код через backend и предлагает завершение после подтверждённого вручения.

## Partner DEV/TEST

`DELIVERY_PARTNER_ENABLED` открывает приём корпоративных отправлений у проверенных организаций. Сотрудники используют текущий Partner App и действующее членство. Регистрация, проверка организации и управление сотрудниками принадлежат существующему Partner API.

Путь `/api/v1/partner/partners/{partnerId}/deliveries` принимает котировки и отправления, возвращает историю и детали, позволяет начать подбор, отменить до забора и получить тестовый код в пути. `GET /totals` под этим путём группирует количество и суммы котировок по статусам. Суммы означают цену по котировке. Котировка принадлежит сотруднику и организации, а подтверждённое отправление доступно активным сотрудникам этой организации. DEV-форма использует явно маркированные синтетические адреса.

## Android E2E

Workflow `Delivery two-app Android E2E` собирает два debug APK для эмулятора, поднимает локальный Spring Boot и PostgreSQL 16, использует синтетические аккаунты и маршруты. Сценарий оформляет отправление через Consumer, выполняет его через Executor и проверяет историю в обоих приложениях. В артефакте `delivery-native-e2e` находятся `status.json` и PNG кадров эмулятора. Подтверждением прогона служит `status: PASSED` для проверяемого SHA. Эти APK предназначены для изолированной проверки UI. Подписанные DEV-сборки выпускаются отдельными workflow.

## Операции и жалобы

В существующем приложении Admin доступны очередь курьеров, список отправлений, аудит переходов, возвраты и жалобы. Для всех операций требуется `DELIVERY_OPERATIONS`. Список отправлений показывает статус, назначение и технические идентификаторы. Адреса и контакты исключены из списка.

Личное отправление можно привязать к существующему обращению через `POST /api/v1/me/support/cases` с `deliveryId`. Backend проверяет владельца и использует существующие лимиты и ключ идемпотентности. Оператор открывает очередь `GET /api/v1/admin/deliveries/complaints` и закрывает обращение через `POST /api/v1/admin/deliveries/complaints/{id}/resolve`. Закрытие фиксируется в существующем журнале обращений.

## Подбор и координаты

Backend повторяет подбор для отправлений в состоянии `SEARCHING_COURIER`, даже если отправитель закрыл экран. Подбор сохраняет тот же порядок кандидатов, пределы времени и транзакционные проверки.

Передача точки для подбора и передача координат по назначению используют разные пути. Назначенный курьер явно отправляет точку через `PUT /api/v1/executor/deliveries/{id}/location` и может прекратить передачу через `DELETE` по этому пути. Владелец личного отправления читает свежую точку через `GET /api/v1/deliveries/{id}/location`. Через две минуты точка перестаёт отображаться. Backend хранит только последнюю точку, удаляет устаревшие точки и очищает точку при выходе из состояний, разрешающих передачу. Вручение подтверждается отдельным кодом.

### Admin в браузере DEV

`bash scripts/admin-web/build.sh` собирает существующий Flutter Admin. `node scripts/admin-web/server.mjs` обслуживает сборку и передаёт только запросы входа, профиля, возможностей и Admin Rides/Delivery в существующий KUNDE DEV API. Админские разрешения проверяет backend. Для разделов Delivery требуется заранее выданный `DELIVERY_OPERATIONS`. Сессия браузера хранится в памяти вкладки. После перезагрузки страницы потребуется вход.
