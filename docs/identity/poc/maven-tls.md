# Maven Central TLS on Windows

## Diagnosis captured for this workstation

- Runtime: Android Studio JBR OpenJDK 21.0.9; Maven: Apache Maven 3.9.9.
- Maven Central's observed leaf certificate was for `repo.maven.apache.org`; the issuer was `AVG Web/Mail Shield Root`, which indicates local HTTPS inspection by AVG Web/Mail Shield.
- A normal Windows `SslStream.AuthenticateAsClient("repo.maven.apache.org")` succeeded with default certificate-chain and hostname checks. Its chain built cleanly to a root present in Windows `CurrentUser\Root` / `LocalMachine\Root`.
- Android Studio JBR did not trust that Windows-installed root in its bundled default `cacerts`, causing Java's `PKIX path building failed`.
- No user Maven `settings.xml` was present and no Maven mirror was configured. The TLS chain, rather than Maven coordinates, was the blocker.

## Rebuild the isolated truststore

From repository root in PowerShell:

```powershell
. .\docs\identity\poc\Initialize-MavenTrust.ps1
```

The script connects to Maven Central with Windows' normal TLS validation, verifies that the final chain root is present in Windows Trusted Root, and imports only that exact public root certificate into `docs/identity/poc/.local/maven-central-windows-root.p12`. It does not accept an invalid chain, disable hostname checks, change global Java files/settings, or import a private key. The truststore, its generated password in the current process environment, Maven distribution and cache live under the ignored `.local` directory. The script exports `MAVEN_OPTS` only for child Maven processes in the current shell.

If Windows cannot validate the chain or the chain root is not in its trusted-root stores, the script stops without importing anything. Resolve that Windows trust issue through the organization/AV administrator; do not use Maven insecure SSL flags or manually download/import an unverified certificate.

## Run backend `verify`

Start the isolated PostgreSQL test dependency and set the credentials generated by the backend POC script:

```powershell
$dbDir = '.\docs\identity\poc\backend-db'
if (-not (Test-Path "$dbDir\.env")) { throw 'Run Start-BackendPoc.ps1 once to generate the local DB secret.' }
docker compose --env-file "$dbDir\.env" -f "$dbDir\compose.yaml" up -d --wait
$env:DB_URL = 'jdbc:postgresql://localhost:5544/kunde_identity_poc'
$env:DB_USERNAME = 'kunde_poc'
$env:DB_PASSWORD = ((Get-Content "$dbDir\.env" | Where-Object { $_ -like 'POC_DB_PASSWORD=*' }) -replace '^POC_DB_PASSWORD=', '')
Remove-Item Env:SPRING_PROFILES_ACTIVE, Env:OIDC_ISSUER_URI, Env:OIDC_AUDIENCE -ErrorAction SilentlyContinue
. .\docs\identity\poc\Initialize-MavenTrust.ps1
$maven = '.\docs\identity\poc\.local\apache-maven-3.9.9\bin\mvn.cmd'
$repo = (Resolve-Path '.\docs\identity\poc\.local').Path + '\m2-identity-poc'
Push-Location .\backend
try { & $maven --batch-mode --no-transfer-progress "-Dmaven.repo.local=$repo" verify } finally { Pop-Location }
```

Use `Start-BackendPoc.ps1 -Provider keycloak` or `-Provider zitadel` to run the local Spring API; the script initializes the same truststore, uses the isolated Maven cache, and keeps `identity-poc` explicitly enabled only for that process.
