# Proposed token lifecycle policy

These initial consumer limits require owner and security approval and a device UX trial. Test realm timeouts are shortened to make the expiry checks repeatable.

| Control | Proposal and rationale | Enforcement owner |
|---|---|---|
| Access token | Start with 5 minutes. It bounds routine post-logout exposure while avoiding frequent refresh on active screens. The observed Spring tolerance was about 60 seconds beyond `exp`, so today's settings could allow about 6 minutes after issuance. Trial an explicit tolerance of at most 30 seconds with clock synchronization and failover tests before adopting it. | Keycloak access lifespan, Spring timestamp policy and infrastructure clock sync |
| Refresh token | Online refresh only. Use the shortest of client idle, SSO idle and absolute session expiry. Keep the refresh token in platform-backed secure storage and keep access tokens in memory. | Keycloak sessions and Flutter storage |
| Rotation and reuse | Enable rotation and set max reuse to zero. Serialize refresh per session and atomically persist the successor. Replay was rejected and the successor subsequently failed in the drill. For an ambiguous exchange, avoid blind replay and recover through a fresh authorization if the token is rejected. | Keycloak settings and Flutter single-flight, storage and recovery |
| Consumer session | Start at 30 minutes idle and 12 hours absolute. This covers an active shopping session without allowing indefinite unattended use. Refresh on demand so background timers do not extend the session indefinitely. Test interrupted checkout and return from background before approval. | Keycloak SSO and client idle/max limits. Flutter scheduling. |
| Logout | Clear local state even if provider logout fails. Use system-browser RP-initiated logout. Reconcile uncertain remote logout and distinguish device logout from sign-out across all devices. | Flutter and Keycloak |
| Device/session revocation | Provide a session list and targeted revoke with recent authentication. Keycloak can terminate online sessions. For restricted accounts and sensitive actions, KUNDE must enforce account/session restrictions at the API within the approved revocation SLO. | Keycloak admin operations through a scoped backend; KUNDE session/identity policy |
| Account compromise | Terminate affected sessions and deny sensitive KUNDE actions immediately through domain policy. Review recovery and audit before restoring access. Reserve emergency signing-key replacement for suspected signing-key compromise. | Security/on-call, Keycloak and KUNDE |
| Key and JWKS | Publish old and new public keys during rotation. Warm each resource server with a new-key canary. Hold passive keys through the longest affected token or session plus tolerance. Monitor unknown-key refreshes and fail closed if a key cannot be resolved. | Keycloak operators and Spring monitoring |

Admin and partner/provider credentials need separate step-up, authentication assurance and session limits based on their risk. A shorter access lifetime increases refresh traffic and makes provider outages more visible. Offline credentials need a separate use case and explicit storage/revocation review. See the [Keycloak session and token settings](https://www.keycloak.org/docs/26.8.2/server_admin/) and [KUNDE token design](../token-architecture.md).
