## Последовательность PR

1. Зафиксировать инвентарь и сопоставление с backlog. Сверить #152 перед изменением общей точки входа. В ADR-019 уточнить, что одна административная Flutter-кодовая база поставляется для закрытого Web и нативных платформ.
2. Добавить проверяемый сервером перечень текущих возможностей сотрудника на основе Identity и действующих грантов. Подключить единый адаптивный Flutter shell и повторно проверить рабочие очереди Rides, Delivery и Auto. Перенос активных разделов по одному позволяет проверить маршруты, вход и выход без изменения их бизнес-правил.
3. В рамках TASK-039 сформализовать назначения ролей и scope. Сервер разрешает операцию, если один действующий грант покрывает само разрешение и все измерения ресурса. Регион и организация определяются из серверной модели ресурса. Области разных назначений не объединяются для одного запроса. Переносить каждый API вместе с негативными тестами списка, деталей и мутаций. Существующие гранты сохраняют текущий DEV-контракт до явной миграции. Управление критическими ролями и возвратами зависит от D-14.
4. Добавить Overview и продуктовые метрики по разрешённым доменным данным. У каждой метрики фиксируются источник, интервал, фильтры, часовой пояс Asia/Almaty и единица измерения. Финансовые показатели публикуются при подтверждённом источнике, с отдельным указанием среды и валюты.
5. Использовать ту же серверную проверку области для партнёров, исполнителей, Customer 360, поиска и поддержки. Добавить управление персоналом после утверждения политики назначений. Затем вывести операции, входящие задачи, аудит, доступные флаги и финансовые отчёты. Изменения состояния флагов требуют рабочего backend-контракта, изменения PROD требуют отдельного согласования.
6. Для интегрированного main проверить backend/Flutter/Security CI, Web и Android E2E, ширины 320/390/600/840/1280/1920 и текст 200%. Собрать Web Release и подписанный DEV APK с проверкой сертификата, non-debuggable и SHA-256. Выполнить отдельную проверку сборки Admin на macOS для iOS.

## Scoped RBAC: контракт первого этапа

| Назначение | Эффективный доступ |
| --- | --- |
| Действующий грант ADR-018 | Прежнее разрешение на уровне платформы. |
| Назначение роли без полей scope | Разрешения роли на уровне платформы. |
| Назначение роли с полями scope | Разрешения роли при совпадении каждого заданного поля: продукт, регион, организация, ресурс. Для отдельного ресурса обязателен продукт. |

Одна запись назначения должна покрывать весь запрос. Серверный вызов без атрибутов ресурса требует платформенного гранта. Истёкшие и отозванные назначения исключаются в БД на каждом обращении, даже если JWT ещё содержит `kunde.admin`. Старые очереди принимают только платформенные гранты, поскольку их запросы пока не фильтруют ресурсы по scope.

V37 добавляет определения ролей, связь ролей с разрешениями, назначения и представление эффективных разрешений. Создание назначений из Admin, аудит их изменений и перенос доменных запросов на scoped-проверки выполняются отдельными этапами. `ADMIN_GRANTS` исключён из разрешений новых ролей. D-14 остаётся открытым.

## Граница этапа Control Center 3.0

Текущий этап включает обзор, Delivery, реестр сотрудников, просмотр действующих разрешений и адаптивную навигацию. Метрики обзора ограничены подтверждённым API Delivery; выдача учитывает действующую область доступа. Остальные продуктовые панели и административные модули откладываются до отдельных заданий. Последовательность выше сохраняет зависимости: сначала scoped-доступ к доменным данным, затем подтверждённые метрики и экраны, после этого сквозные проверки. Управление критическими назначениями и финансовые подтверждения зависят от D-14.
