# Placement registry: table-name prefix -> how the table is placed when operational data is split by city.
# First matching line wins (specific prefixes above generic ones). A table without a line fails PlacementRegistryTest.
# Format: <schema>.<table-prefix>=<class>
#   GLOBAL                    always on the global database (identity, partners, reference data, city registry)
#   CITY_ROOT                 aggregate root; owns a nullable-until-backfilled, immutable city_id column (V67)
#   CITY_CHILD:<root table>   placed by its root through foreign keys; MUST NOT carry its own city_id
#   EXECUTOR                  global identity of a driver/courier/specialist who may work in several cities;
#                             per-city availability is future work and is NOT placed by a single city_id
#   LOCAL                     per-database infrastructure (outbox, inbox): every database, global or shard, has its own copy
#                             and a row stays in the database of the transaction that wrote it; never moved between databases
#   UNDECIDED:<reason>        placement cannot be decided from code alone; blocks physical sharding until resolved
# See docs/architecture/database-sharding-readiness.md section 4.
